# Guardrails and activation

These controls are implemented in the checkout. They are not activated on production merely by building it. No live database migration or deployment is performed by the implementation tests.

## Activation order

1. Back up the database, review the new migration, and run `npm run db:migrate` with an operator connection. The migration drops unused OAuth bearer tokens while preserving identity links. It seeds runtime policy with signup, newsletter writes, AI, uploads and email **disabled**. Reading existing rooms, exports and realtime remain enabled. Missing/malformed policy or database outages deny protected requests.
2. Set a new independent random `SOCKET_SIGNING_SECRET` on both web and realtime deployments. Existing socket tokens will require reconnecting. Keep `NEXTAUTH_SECRET` stable: it also keys privacy-preserving rate-limit and invitation hashes.
3. Create a managed Turnstile widget for the exact frontend hostname and configure `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (build-time public key), `TURNSTILE_SECRET_KEY` (server only), and an exact `NEXTAUTH_URL`. The server validates success, hostname and action. Password signup/login and verification email requests require a valid token. No test-key fallback exists in application code. Configure this through the existing Cloudflare account using `cf` for this project; no Wrangler config exists.
4. Web on Vercel accepts its overwritten single `x-forwarded-for` address. Other web ingress is denied unless `TRUSTED_PROXY_IP_HEADER=x-study-client-ip` is set and that ingress **strips client-supplied values** before injecting its own value. Never set this option just to make arbitrary headers work. Realtime uses the actual TCP peer address when no verified client header is available. On Render this may group clients behind a proxy; it is conservative and not a claim of accurate per-client IP attribution.
5. Configure a verified `RESEND_FROM` and server-only `RESEND_API_KEY`. All accounts, including existing password and OAuth users, verify their mailbox in `/account` before new room membership or paid features. OAuth sign-in alone is not treated as verified mailbox ownership. Verification messages themselves are CAPTCHA-gated, limited per user/email/IP and charged to global email caps.
6. Review a complete policy JSON, then run `npx tsx scripts/guardrails.ts set policy.json`. Use an operator connection, not the restricted runtime role. `status` prints policy and global counters; no user/email/credential values. Runtime switches take effect for new requests without a deployment. In-flight provider work can complete within its deadline; disconnect checks run every two seconds.
7. Review `scripts/database-role.sql`, create a restricted runtime login and apply its grants. Use it for web/realtime, with an operator login only for migrations/policy/maintenance. RLS is not introduced: route ownership remains the tenant boundary. RLS requires a separate tested tenant-context design rather than policies bypassed by the current owner role.
8. Enable GitHub variable `GUARDRAIL_RETENTION_ENABLED=true` and add a restricted maintenance secret `GUARDRAIL_DATABASE_URL` to environment `production-maintenance`. The scheduled job deletes at most 50 expired rooms per run and fails when global counters reach 80%. Configure GitHub failure notifications and a Sentry issue alert for operation `guardrail.threshold`. These external settings are not verified by local tests.

## Defaults and accounting

Policy limits: 1,000,000 AI token units/day, 10,000,000/month, 500 AI calls/day; 100 emails/day and 1,000/month; 50 uploads/day; 20 hosted rooms/user, 20 documents/room, 1,000,000 extracted characters/room, 50,000,000 extracted characters globally, and 30 participants/room. Each room has at most 100 quiz rounds.

AI units reserve **UTF-8 input bytes + per-message overhead + maximum output tokens**. Input allowance is at most 16,000 and output at most 3,500 (answers 1,800). These are deliberately conservative usage ceilings, not a dollar spend estimator. Models/prices cannot evade token and call ceilings. Requests use no automatic AI retries, a 30-second provider timeout and a 45-second enclosing work deadline. Reservations are never refunded, including uncertain failures. Every permitted provider attempt is charged centrally, including operator evaluation scripts.

All counters are shared in PostgreSQL and reserved atomically under a lock row. Partial reservations roll back. Fixed windows use UTC; crossing a window boundary allows the next window's allowance. Safety-store errors deny access. Global 80% threshold crossings persist audit events and send sanitized Sentry issues when configured. Policies can be edited or set to zero to stop further admission. A disabled feature returns 503; exhausted limits return 429.

HTTP JSON bodies are bounded to 16 KiB using actual stream bytes, regardless of `Content-Length`; multipart uploads are bounded to 4 MiB plus 32 KiB overhead. PDFs are checked for extension/signature, limited to 100 pages/180,000 extracted characters, and processed in a worker terminated after 10 seconds. Local model work uses a worker with a 15-second per-task deadline and at most four queued jobs. Uploads and PDF exports use shared leases. Timed-out worker jobs are terminated rather than continuing inference in the background. Model downloads/cold starts may exceed the budget; warm the cache operationally before enabling uploads. Summary generation considers at most 20 topics and generates at most three extra explanations.

Report delivery reserves one durable `(room, participant)` record **before rendering or sending**. A report can be delivered once per participant per room. Ambiguous failures stay reserved; an operator must reconcile delivery at the provider before manually resetting a record. This avoids repeating a send after the provider's idempotency cache expires. Email destinations come from verified current user records, never arbitrary request addresses.

## Access, privacy and moderation

Existing members retain access unless revoked. New members require a separate 256-bit invitation, stored only as a keyed hash, expiring after 24 hours. URLs carry the credential in a fragment to avoid sending it in HTTP URLs/referrers; the client removes it after successful enrollment. Hosts can revoke invitations/remove participants. Removed members cannot reenroll; removing a member also revokes existing invitations. Realtime verifies membership per action and disconnects revoked/deleted accounts within the next two-second access check. A database error during that check disconnects clients. Tokens expire after 30 minutes; clients reacquire them using their web session. Socket origin and connection/user/action limits apply before handlers.

Accounts, hosted rooms and active documents have authenticated deletion APIs. Account deletion removes hosted rooms, personal quiz submissions/feedback/questions, memberships, newsletter and verification records; audit actor identifiers are anonymized. Quiz-source references are removed before source deletion. Room deletion removes related content through explicit deletion plus database cascades. Deleting an active document removes its related generated messages/quizzes. Archived documents are removed by deleting their room. Account and room deletion are surfaced in Account; active document deletion is available in the room library and through its host-only API.

Default scheduled room/audit retention is 90 days (policy permits 7–365); unsubscribed newsletter records are purged after 30 days. Accounts persist until deletion. This job must be enabled and run regularly; the code alone does not prove it is scheduled in production. Privacy disclosures describe processors, security checks, retention and deletion. OAuth bearer tokens are not retained; provider identity links are preserved.

Generated guidance is labelled in room answers, summaries and PDF exports. Members can report messages and hosts can remove them; reports store a category and internal IDs, not content. Operators review reports through the audit database. There is no automatic semantic content classifier or claim of guaranteed prompt-injection resistance. Documents/questions are treated as untrusted input; the app grants the LLM no tools or authority. Grounding/schema checks remain active. Socket errors expose only deliberate safe errors, not arbitrary provider/database exception messages.

## Verification

`npm test` exercises real PostgreSQL quota SQL using an ephemeral in-memory PGlite database, concurrent cap reservations, rollback, missing/invalid policy, database failure, body-byte limits and CAPTCHA success/action/hostname/outage/replay behavior.

After `npm run build`, run `npm run test:guardrails:integration`. It applies **all actual migrations with pgvector**, starts the production Next.js app and realtime server against an ephemeral PostgreSQL socket, and replaces provider traffic only in a test preload. It checks email verification/one-use links, anonymous and cross-user route denial, host-only uploads, kill switches/cap exhaustion with **zero AI calls**, invitation enrollment/revocation, active-socket disconnection, permanent email deduplication and room/account deletion, including rejection of deleted users with existing sessions. The preload forbids other external traffic. It is never used by application startup. These tests do not contact production, prove external credentials, or establish live provider behavior.

Compatible `sharp` and `source-map-js` patches were applied. The remaining npm advisories are in Tailwind build-time dependencies; resolving them requires a separately tested toolchain upgrade. Local verification uses the installed Node 24 runtime; CI pins the supported Node 22 runtime.
